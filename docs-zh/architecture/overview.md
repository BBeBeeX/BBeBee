# 总览与核心架构决策

> **历史章节映射：** 原 `docs-zh/01-overview.md`。

> **本文回答什么。** BBeBee 是什么、刻意*不是*什么、面向哪些平台，以及其余一切所依赖的五个架构决策。如果写代码前只读一份文档，请读本文与 [02](./layers.md)。

---

## 1. 我们在构建什么

一款用同一份代码库同时运行在桌面端与移动端的音乐播放器：播放器本身保持精简，几乎所有行为都以插件形式提供，而**音源则以用户粘贴进来的文本形式到达**。

用户可见的产品很普通：曲库、队列、带均衡器的播放、离线下载、播放列表、歌词，以及从不止一处获取音乐的能力——磁盘上的一个文件夹、一台自托管服务器、任何一段源字符串所描述的来源。底下的形态有两处不寻常。不存在一个拥有这些功能的特权"核心"：曲库是一个插件，下载器是一个插件，下载器所使用的文件系统访问同样是插件。而且音源根本不是一个包——它是用户导入的一份 JSON 文档，由一个内置运行时解释（[ADR-5](#adr-5--音源是导入的字符串由一个运行时解释)）。在视觉上，应用遵循一种沉浸式的、暗色优先的流媒体美学——纯黑的机壳、深炭灰的画布、鲜绿色的播放点缀、几何怪诞体（geometric grotesque）字体、以及药丸形的交互控件——详见 [UI 架构](../ui/design-system.md#6-多主题色彩系统与视觉标识)。

### 为什么这样构建

三条理由，按重要性排序：

1. **跨平台而不写条件分支。** 服务抽象的替代方案是让 `Platform.OS === 'ios' ? … : …` 散落在代码库各处，这会迅速腐化。在这里，平台差异只表达一次——以*加载了哪个插件*的形式——此后不再出现。
2. **音源天然是多元且不稳定的。** 每个后端都有不同的 API、不同的认证、不同的分页方式，以及不同的寿命——而且会在毫无预警的情况下变化。因此，音源不可能是某种由我们编译、评审、发布的东西：它必须是用户能在几分钟内在应用里添加、编辑和修复的东西。这正是音源是*字符串*而不是包的原因（[06](../sources/spec.md)），其余的音源设计也都从这一决策推导而来。
3. **生命周期正确性很难，而 Cordis 已经解决了它。** 注册事件监听器、打开套接字、持有音频节点、启动定时器的插件，在停用时必须把这些全部拆除。Cordis 的 fiber/effect 模型从构造上保证卸载是彻底的——这恰恰是大多数插件系统做错的部分。

### 目标

- 一张插件图，在 iOS、Android 与桌面端上无需修改即可运行。
- 插件可在运行时停用且不留痕迹——没有监听器、没有定时器、没有套接字。
- 新增一个音源只需导入一个字符串——无需构建、无需发版、无需安装。
- 音频路径在*所有*目标平台上都支持真正的 DSP 链（参数均衡 EQ、动态处理、卷积），而不只是桌面端。
- 离线优先：没有网络时，曲库与队列依然可用，应用依然可以导航。

### 非目标

在此明确写出，因为其中任何一条若被重新引入，都会改变架构。

- **不是 DRM 客户端。** 不集成 Widevine/FairPlay。需要 DRM 的音源超出范围；`StreamHandle` 类型预留了一个 `drm` 字段，门没有焊死，但没有任何实现。
- **不是服务器。** 不构建同步后端。跨设备同步被设计为一个 SPI（附带文件/WebDAV 参考实现），推迟到 M5 之后。
- **不为第三方服务随附音源。** 运行时对内容中立，且能表达的东西很多，但本仓库只随附解释器、本地文件提供方，以及一小批面向开放自托管协议的源文档——Subsonic/Navidrome、Jellyfin、纯 HTTP URL、播客订阅源——用作演练示例和测试。用户导入什么是他们自己的选择；导入界面会写明某个音源将要做什么、将要与谁通信，应用除此之外不加任何评判（[06 §8](../sources/runtime.md#8-信任导入的源能做什么不能做什么)）。
- **不是通用扩展宿主。** 插件是第一方包，在两个目标平台上都静态打包。导入的*音源*才是扩展机制所在，而约束它们的是一道真正的解释器边界，而不是插件能力模型——后者被如实描述为*纵深防御，而非沙箱*（[03 §7](../plugins/capabilities.md#7-能力模型)）。
- **范围内不做 Web 构建。** React Native Web 在技术上可行，但下文的决策 **ADR-2** 为桌面端选择了独立的 DOM UI，而浏览器目标会成为第三个外壳且没有离线方案。日后可重新审视；当前没有计划。

## 2. 目标平台

| 目标 | 宿主 | JS 运行时 | 内核所在 | UI |
|---|---|---|---|---|
| iOS | Expo / React Native | Hermes | 应用的唯一 JS 上下文 | React Native |
| Android | Expo / React Native | Hermes | 应用的唯一 JS 上下文 | React Native |
| 桌面端（macOS / Windows / Linux） | Electron | V8，渲染进程 | **渲染进程** | React DOM |

移动端需要**自定义开发构建**（`expo-dev-client`），而非 Expo Go，因为 `react-native-audio-api` 和若干核心服务模块包含原生代码。开篇即说明这一点，是因为它影响每一位贡献者的上手指引。

## 3. 架构决策（ADR）

前四项在设计写就之前即已敲定；**ADR-5 是后来做出的，它重写了 ADR-1 的论证**——这一点在此如实记录，而不是悄悄修补。每一项都记录了选择了什么、否决了什么，以及代价是什么。

### ADR-1 —— 插件在所有目标平台上都静态打包

> **经 [ADR-5](#adr-5--音源是导入的字符串由一个运行时解释) 修订。**
> 本决策原文为*"移动端静态打包，桌面端可运行时加载"*，其全部论证是：桌面用户不应为了获得一个新的音源而依赖项目发版。音源不再是包，这一论证随之消失，而 ADR-1 当初否决的选项如今成了决策本身。

**决策。** 一份插件清单格式，一个加载器。一个代码生成步骤在两个目标平台上都为工作区中的每个插件发出静态 `import` 语句；配置只负责启用、停用与配置它们。面向用户的可扩展性存在于导入的**源字符串**（[06](../sources/spec.md)）之中，而不是存在于可加载的插件代码里。

**已否决——保留桌面端动态加载器。** 它能用，为它做的设计也依然成立（[loading.md §6.2](../plugins/loading.md#62-桌面端动态加载--plugin-loader-dynamic) 详述了桌面端动态加载实现）。否决它作为*原始*范围的理由是：它当初服务的对象——音源——如今在两个平台上都以数据形式到达，而剩下适合它做的事（第三方音效、scrobbler、歌词提供方）还不足以证成一整套安装/更新/隔离流程、一个能力授予 UI，以及 [capabilities.md §7](../plugins/capabilities.md#门实际运行的位置) 自己也承认在桌面端并不成立的那种逐插件门禁。

**已否决——双端运行时插件市场。** 理由同上，此外：在 iOS 上，下载并执行新 JavaScript 需要一个解释器沙箱。那个沙箱如今已经因为另一个理由（ADR-5）而存在，所以如果日后重新审视此问题，起点会好得多。

**代价。** 第三方插件作者必须把自己的包打进构建里，因此在沙箱普及之前，非音源扩展实际上都是第一方的（[10 §M5](../roadmap/roadmap.md#m5--沙箱上的第三方扩展)）。移动端与桌面端在插件集合上不再漂移，这消除了整整一类"贡献的视图缺席"的兜底处理——不过处理代码仍然保留，因为 ADR-2 会出于自己的理由造成同样的状态。

### ADR-2 —— UI 拆分：移动端 React Native，桌面端 React DOM

**决策。** 两个外壳、两套组件库、一个无头核心。插件贡献与渲染器无关的**描述符**（descriptor：一条路由、一个槽位填充、一条命令、一个设置页），并在独立的包中为各目标平台随附视图实现。

**已否决——通用 React Native Web。** 只有一份 UI 代码库，Electron 渲染同一个 bundle，成本大约省一半。否决的原因是：桌面音乐播放器理应具备的交互——可调整大小的多栏曲库、右键上下文菜单、拖拽重排队列、键盘导航、原生窗口边框、托盘迷你播放器——恰恰是 react-native-web 会做得别扭的那些东西。在视图层花两倍的钱，换来的是一个用起来像桌面应用的桌面应用。

**代价。** 每个带 UI 的插件最多变成三个包。两套必须保持同步的 design-token 流水线。两套导航系统。一个纪律问题：把逻辑写进视图现在*成为可能*，架构必须主动阻止它（[08 §4](../ui/architecture.md#4-把服务绑定到-react)）。

### ADR-3 —— Electron 内核位于渲染进程；`main` 是一个薄的原生宿主

**决策。** Cordis `Context` 创建在渲染进程中。`main` 进程持有 Node 与操作系统，通过 `contextBridge` preload 暴露一个狭窄的、以能力划定范围的表面，并且**不含任何业务逻辑**。桌面端的核心服务插件只是这层 IPC 表面之上的薄客户端。

**已否决——拆分内核（服务在 main，UI 内核在渲染进程）。** 这能让下载与播放在窗口关闭后继续存活。否决的原因是它引入了一个序列化边界和一层远程服务代理，而移动端没有对应物，这意味着插件图会随平台而异——正是本架构要避免的东西。

**已否决——内核只在 main。** 与移动端的分歧最大；UI 插件将完全无法共享内核。

**后果。** 桌面端与移动端都恰好有一个 JS 运行时，承载恰好一个 context。功能插件无法分辨自己身处哪个平台。代价是桌面端的后台工作与渲染进程的生命周期绑定——用"关闭窗口到托盘"来缓解，而不是靠架构。见 [02 §4](./layers.md#4-后台意味着什么)。

### ADR-4 —— `react-native-audio-api` 是所有目标平台上首要的播放与 DSP 引擎

**决策。** `ctx.audio` 服务契约就是 **Web Audio API**。在 iOS 与 Android 上由 `react-native-audio-api` 满足；在 Electron 渲染进程中，由同一个包的 web 实现（或浏览器原生 Web Audio——两者是同一接口）满足。

正是这一决策使 DSP 需求变得可控。没有它，"移动端音频效果"意味着把原生 DSP 写两遍。有了它，十段均衡器就是一条 `BiquadFilterNode` 级联，在三个平台上行为完全一致。

**已否决——移动端使用 `react-native-track-player`。** 它在后台队列、锁屏控制与蓝牙/车机集成方面久经考验。否决的原因是它不暴露音频图，这会让 EQ 与音效成为桌面端专属——等于放弃一个已声明的目标。

**已否决——`expo-audio`。** 最简单，且停留在托管工作流内，但既没有队列引擎，也没有 DSP 图。

**代价与缓解。** `react-native-audio-api` 目前处于 `0.13.x`——1.0 之前，API 仍在变动。缓解手段是结构性的：`ctx.audio` 与其他服务无异，因此可以在其背后替换另一个引擎，而不触碰 `ctx.player` 或任何音效插件。这个抽象*本身就是*保险单。已作为最高优先级事项记录在风险登记册中（[10 §3](../roadmap/roadmap.md#风险登记册)）。

### ADR-5 —— 音源是导入的字符串，由一个运行时解释

**决策。** 音源是一份**用户以文本形式导入的 JSON 文档**——粘贴、从 URL 抓取、从文件打开，或扫描二维码得来——存储为一行记录，由唯一的内置运行时 `plugin-source-runtime` 解释。文档以一门小型选择器/模板语言声明自己的端点和一组**规则**；每一次抓取、选取与类型强转都由运行时完成。这就是把 [legado](https://github.com/gedoor/legado) 的书源模型应用到音频上，具体规定见 [06](../sources/spec.md)。

**已否决——每个后端一个插件包**（旧设计）。每个音源都是一个实现提供方 SPI 的 `plugin-source-*` 包。这是更强大的选项：任意代码都能处理任意后端，还带类型与测试。否决的原因是它让项目处在每一次修复的必经之路上。后端把一个 JSON 字段改了名，用户对此无能为力：必须有人写 TypeScript、开 PR、通过评审、剪裁发版——而且在移动端（那里不允许运行时加载）还得走应用商店上架。对一类按别人的日程变化的后端来说，"每坏一次发一版"算不上一种维护方案。

**已否决——音源作为完全不含代码的声明式配置。** 更安全，也更容易推理，但它一接触现实就会失败：真实的后端需要一个计算出来的签名、一个从上一个响应里取出又用进下一个请求的令牌、一个时间戳、一个 MD5。一门没有任何逃生舱口的音源语言，只能产出*差点就能用*的音源，而绕过它的手法比逃生舱口本身更糟。

**后果——每一条都在别处承重：**

- **能力是推导出来的，不是声明出来的。** 一个音源能做什么，取决于它包含哪些规则块，因此旧的"少声明/多声明"失败模式不复存在（[06 §1.3](../sources/rule-engines.md#13-能力是推导出来的不是声明出来的)）。
- **真正的沙箱从"推迟"变为"强制"。** 源规则是陌生人写的代码，因此 `ctx.js`——一个独立的 QuickJS realm，带可枚举的宿主 API 和按源划分的宿主允许列表——是随该功能一起交付的核心服务（[04 §19](../services/contracts.md#19-ctxjs--沙箱化求值器)、[06 §8](../sources/runtime.md#8-信任导入的源能做什么不能做什么)）。插件系统自身的围栏缺口（[capabilities.md §7](../plugins/capabilities.md#它不是什么)）也顺带得到了答案。
- **ADR-1 失去了它存在的理由**，已在上文修订。
- **诊断成为随附交付的功能。** 当音源归用户所有时，"为什么它突然不能用了"就是用户的问题，因此 [06 §10](../sources/authoring.md#10-诊断一个坏掉的源) 中的按功能测试界面与其流式追踪不是一件碰巧留在构建里的开发者工具——它是整个模型的维护方案。

**代价。** 一门规则语言、一个解释器、一个沙箱、一套导入/导出流程、一个编辑器和一个调试器——这一切都要在第二个音源跑通之前备齐。类型安全止步于文档边界：一条坏规则是报错信息友好的运行时错误，而不是编译错误。后端一变，音源会无声地腐烂，因此 `RuleError`、过期徽章与健康检查（[06 §7](../sources/authoring.md#7-错误)）的存在就是为了让腐烂可见。而且应用现在会运行它没有亲手写过的代码，这是一种需要持续维护的安全姿态，而不是打一个勾就完事。

## 4. 术语表

以下术语在整套文档中始终按此处给出的精确含义使用。

| 术语 | 含义 |
|---|---|
| **Layer 0–5** | [02 §1](./layers.md#1-分层模型) 的六个层：**0** 协议、**1** 内核、**2** 核心插件、**3** 日志传输、**4** 功能插件、**5** UI 与业务功能。一个包所在的层决定了它可以导入什么；Layer 2 是唯一被允许触碰平台 SDK 或驱动内核的层，Layer 3 是唯一被允许写控制台的层。 |
| **内核（Kernel）** | `@BBeBee/kernel` —— Cordis 再加上 BBeBee 的引导启动、配置加载、插件解析与能力门禁。Layer 1。不是 Cordis 的概念。 |
| **Context**（`ctx`） | 一个 Cordis `Context`。同时是 DI 容器、事件总线与生命周期作用域。每个插件都会获得自己的派生上下文。 |
| **服务（Service）** | 在稳定的服务键（`ctx.fs`）上认领的一种能力。在 `@BBeBee/protocol` 中声明，在给定隔离作用域内任一时刻恰好由一个插件提供。 |
| **Fiber** | Cordis 中插件生命周期的单位。跟踪状态（`PENDING` → `LOADING` → `ACTIVE` → …），持有插件的可清理项（disposables），并在插件依赖变化时重新加载它。 |
| **Effect** | 通过 `ctx.effect()` 注册的一个可逆副作用。返回的 disposer 会在卸载时自动运行。 |
| **核心插件** | 实现某个平台服务的插件。位于 `packages/core/*`。Layer 2 —— 唯一被允许导入平台 SDK 的代码，也是唯一被允许调用内核引导表面的代码。 |
| **功能插件** | 不属于核心插件或日志传输的一切无头（headless）内容。Layer 4。只通过服务键触达平台，也只通过 `ctx.logger` 记日志。 |
| **日志传输（Log transport）** | 订阅 `ctx.logger` 并把日志行送到某个去处（环形缓冲区、控制台、滚动文件）的插件。Layer 3。从外壳的引导数组中加载，因此在第一个功能插件启动之前它已在运行。 |
| **源（Source）** | 用户所配置的一个音乐后端。以 `sourceUrl` 标识，通过派生的 **source id** 寻址。两台 Navidrome 服务器就是两个源。 |
| **源字符串（Source string）** | 源的可导入文本形式：一份 JSON 文档，或其构成的数组（一个 *source set*）。用户分享的单位。 |
| **规则（Rule）** | 源文档中的一个字段，以 [06 §3](../sources/rule-engines.md#3-规则语言) 的选择器/模板语言编写。 |
| **源运行时（Source runtime）** | `plugin-source-runtime` —— 源文档的唯一解释器。把每个启用的源以 `MediaProvider` 的形式呈现给 `ctx.sources`。 |
| **提供方（Provider）** | `ctx.sources` 所消费的内部接口。恰好有两个实现：源运行时的按源适配器，以及 `plugin-source-local`。不是扩展点。 |
| **URN** | `BBeBee:<sourceId>:<kind>:<id>`。曲库实体的稳定标识符。 |
| **绑定（Binding）** | `media_bindings` 表中的一行，把某个曲目 URN 绑定到具体的本地文件。"这首曲目已下载"的实际含义即在于此。 |
| **链（Chain）** | 播放器的源节点与输出之间的一串有序 DSP 效果。 |
| **描述符（Descriptor）** | 一种与渲染器无关的 UI 贡献——一条路由、槽位填充、命令或设置页——由当前运行的外壳解析为真实组件。 |
| **外壳（Shell）** | 挂载 UI 的宿主应用：`apps/mobile` 或 `apps/desktop/renderer`。Layer 5，但其**组合根（composition root）**除外 —— 即把 Layer 2 的实现接入内核的那对 `boot.ts`/`plugins.ts` 文件。 |
