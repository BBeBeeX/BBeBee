# Internationalization Architecture (`ctx.i18n`)

> **What this answers.** How interface strings are organized, resolved, and switched at runtime across desktop and mobile without third-party i18n dependencies (`@bbebee/plugin-i18n`, Layer 4).

---

## 1. Contract (`I18nService`)

Declared in [`packages/protocol/src/services/platform.ts`](../../packages/protocol/src/services/platform.ts) and implemented by `@bbebee/plugin-i18n`:

```ts
export interface I18nService {
  readonly locale: string
  t(key: string, params?: Record<string, string | number>): string
  register(namespace: string, catalogues: Record<string, Record<string, string>>): Disposable
  onLocaleChange(cb: (locale: string) => void): Disposable
}

declare module 'cordis' {
  interface Context {
    i18n: I18nService
  }
}
```

Language switching is driven by `ctx.settings` (`AppSettings.language: 'zh' | 'en' | 'system'`) rather than a direct setter on `ctx.i18n`. When `settings.language` changes, `plugin-i18n` re-resolves `locale` and notifies all `onLocaleChange` subscribers.

## 2. Key Format & Namespace Conventions

### 2.1 Key syntax

Every translation key uses the `namespace:path.to.key` format:

```ts
ctx.i18n.t('app:common.confirm')
ctx.i18n.t('registry:filter.showThirdParty')
ctx.i18n.t('settings:github.endpointLabel', { index: 1 })
```

- **Separator:** The first `:` splits the `namespace` from the dot-separated `path`.
- **Nested or flat JSON:** Built-in JSON catalogues may use nested objects (`{ "common": { "confirm": "OK" } }`) which are flattened to dot-paths (`common.confirm`) at load time. Catalogues passed to `ctx.i18n.register()` use flat dot-paths (`{ "filter.showThirdParty": "..." }`).
- **Pluralization:** ICU message syntax is intentionally not used. Callers select explicit keys based on count (e.g. `items.one` vs `items.other`) and pass `{ count }`.

### 2.2 Built-in namespaces

`@bbebee/plugin-i18n` ships built-in catalogues under `packages/feature/plugin-i18n/src/locales/`:

| Namespace | Source File(s) | Purpose |
|---|---|---|
| `app` | `src/locales/en.json`, `src/locales/zh.json` | Common actions (`confirm`, `cancel`, `retry`, `save`, `delete`), status labels (`loading`, `empty`, `error`, `offline`), and units |
| `registry` | `src/locales/registry.json` | Community content registry UI (`registry:filter.*`) and route title (`registry:route.discover`) |
| `settings` | `src/locales/settings.json` | Settings UI strings (`settings:github.*`) |

### 2.3 Interpolation (`{var}`)

Placeholders use `{name}` syntax and are replaced from `params`:

```ts
ctx.i18n.t('settings:github.endpointLabel', { index: 2 })
// en → "Acceleration endpoint 2"
// zh → "加速线路 2"
```

If a placeholder is missing from `params` (or `params` is omitted), `t()` preserves the literal `{name}` token in the returned string and logs a deduplicated warning via `ctx.logger.warn` once per `(key, param)` pair.

## 3. Locale Resolution & Key-Granular Fallback

### 3.1 Locale resolution chain (`settings.language`)

1. **Explicit setting (`'zh'` or `'en'`):** Used directly after BCP 47 negotiation.
2. **`'system'`:** Reads `ctx.device.locale` (backed by `core-device-desktop` / `@tauri-apps/plugin-os` on desktop and `core-device-mobile` / `Intl` on mobile; no platform SDK is imported in `plugin-i18n`).
3. **BCP 47 negotiation (`negotiateLocale`):** Normalizes underscores to hyphens, lowercases the tag, and strips subtags from right to left against the set of registered locales (`zh-Hant-HK` → `zh-hant-hk` → `zh-hant` → `zh`, `fr-FR` → `fr-fr` → `fr`). If no registered catalogue matches, falls back to `'en'`.

### 3.2 Key-granular fallback (`t()`)

Each `t(namespace:path)` call resolves per key:

```
active locale catalogue → 'en' catalogue → raw key string
```

- **No whole-language demotion:** If `zh` is missing 3 keys in a namespace, only those 3 keys fall back to English; all other keys continue rendering in Chinese.
- **Third-party plugin isolation:** A third-party plugin that registers only `{ en: { ... } }` renders its strings in English while the rest of the application stays in Chinese.
- **Never empty:** `t()` never returns `""` or `undefined`. When both the active locale and `'en'` miss, `t()` logs a deduplicated warning via `ctx.logger.warn` and returns the raw `key`.

## 4. Registering Plugin Catalogues (`ctx.i18n.register`)

Feature or third-party plugins register their own namespace through `ctx.i18n.register(namespace, catalogues)` inside `ctx.effect()` so unloading the plugin automatically disposes its strings:

```ts
import type { Context } from '@BBeBee/protocol'

export const name = 'plugin-my-feature'
export const inject = ['i18n']

export async function apply(ctx: Context) {
  ctx.effect(() =>
    ctx.i18n.register('my-feature', {
      en: {
        'header.title': 'My Feature',
        'status.items': '{count} items',
      },
      zh: {
        'header.title': '我的功能',
        'status.items': '{count} 项',
      },
    }),
  )
}
```

- **Namespace isolation:** Multiple registrations under the same namespace stack in registration order (latest wins per key). Calling the returned `Disposable` removes only that registration's entries without affecting other namespaces or earlier layers.

## 5. Consuming Translations in UI (`useI18n`)

Both `@BBeBee/ui-kit-desktop` and `@BBeBee/ui-kit-mobile` export `useI18n(ctx: Context)`:

```ts
import { createElement as h } from 'react'
import type { Context } from 'cordis'
import { useI18n } from '@BBeBee/ui-kit-desktop' // or '@BBeBee/ui-kit-mobile'

export function ExampleView({ ctx }: { ctx: Context }) {
  const { t, locale } = useI18n(ctx)
  return h('button', { type: 'button' }, t('app:common.confirm'))
}
```

- **No React Context Provider:** Following the three-package UI convention ([ui/architecture.md](../ui/architecture.md)), `ctx` is passed as a component prop and handed directly to `useI18n(ctx)`.
- **Live re-render:** `useI18n` subscribes to `ctx.i18n.onLocaleChange`, updating `locale` and returning a fresh `t` callback reference whenever the active language changes, so memoized option arrays (`useMemo(..., [t])`) recompute automatically.
- **Route & Tray Titles (`RouteContribution.title`):** Plugins may supply an i18n key (e.g. `title: 'registry:route.discover'`) in `RouteContribution`. Both the desktop shell (`Shell.tsx`, `TopBar.tsx`) and mobile shell (`App.tsx`) subscribe via `useI18n(ctx)` and translate any title containing `:`.

## 6. Catalogue Completeness Check (`check-locales.mjs`)

Built-in catalogues (`en.json` vs `zh.json`, plus the `en`/`zh` halves of `registry.json` and `settings.json`) are checked for key parity by:

```bash
pnpm check:locales
# or: node packages/feature/plugin-i18n/scripts/check-locales.mjs
```

Any key present in `en` but missing in `zh` (or vice versa), or any empty string value, fails with a non-zero exit code in CI (`.github/workflows/ci.yml`). Third-party catalogues registered at runtime via `ctx.i18n.register()` are not subject to static parity checks and rely on key-granular runtime fallback (§3.2).

---

## 7. Integration Checklist

- [ ] Follow `namespace:path.to.key` naming (`camelCase` segments, domain-scoped namespace).
- [ ] Provide both `en` and `zh` entries when adding keys to `packages/feature/plugin-i18n/src/locales/*.json`.
- [ ] Run `pnpm check:locales` to verify `en` / `zh` key parity and non-empty strings.
- [ ] If registering from an external plugin, wrap `ctx.i18n.register(...)` in `ctx.effect()` so strings are cleaned up on plugin unload.
- [ ] In React / React Native components, call `const { t } = useI18n(ctx)` from `@BBeBee/ui-kit-desktop` or `@BBeBee/ui-kit-mobile` (never import a third-party i18n library).
- [ ] Verify live language switching (`en` ↔ `zh`) in component tests without remounting.
