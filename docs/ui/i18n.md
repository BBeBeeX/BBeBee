# i18n Contribution Guide

How user-visible text is internationalized in BBeBee. The normative rules live in
[`rules/i18n.md`](../../rules/i18n.md); this is the contributor-facing walkthrough.

## The model

- Every UI string is a **key**, never a hardcoded literal: `t('namespace:path.to.key')`.
- Keys live in **catalogues** shipped by `@BBeBee/plugin-i18n`
  (`packages/feature/plugin-i18n/src/locales/`): `en.json`/`zh.json` for the
  `app` namespace, one `<ns>.json` (`{en, zh}` side by side) per plugin namespace.
- At runtime `ctx.i18n` resolves `t()` per key: current locale → `en` → the key
  itself. A missing key degrades to a readable identifier, never a blank label.
- No third-party i18n libraries. The `ctx.i18n` service is the only mechanism.

## Key format

`namespace:path.to.key` — e.g. `t('library:playlistDetail.addTracksToFill')`.

- **namespace** is the owning plugin's domain (`library`, `sources`, `settings`,
  …) or `app` for shared kit (`packages/ui/ui-kit-*`, `apps/*`). Never put one
  plugin's keys in another plugin's namespace, and never stuff everything into
  `app` to save effort.
- **path** groups by screen/component (`playlistDetail`, `nowPlayingStyles`, …).
- **key** is lowerCamelCase derived from the English text.
- Interpolation uses `{param}` placeholders: `t('x:y.deleteItem', { title })`.
  Never concatenate sentences from fragments — Chinese and English word order
  differ. Plurals split into `one`/`other` keys; the call site picks by count
  with full literal keys (no runtime key assembly).

## Writing UI code

```tsx
// Have ctx → use the hook. Never read ctx.i18n directly (it throws when the
// service is absent; the hook degrades gracefully).
const { t } = useI18n(ctx)
return <button aria-label={t('library:index.addFolder')}>{t('library:index.addFolder')}</button>
```

- Components without `ctx` get it threaded down from the owning screen (the
  established precedent), or receive pre-translated labels from the call site.
- `en` catalogue values are **verbatim** source text — carry it over, don't
  polish. Do not reword English when extracting.
- `zh` translations follow the terminology table in `rules/i18n.md` §4.
- Do not extract: comments, logs, test assertions, React keys, storage keys,
  URLs, brand names, data samples, example values.

## Third-party plugins

Third-party catalogues are **not** part of the static checks. Register at runtime:

```ts
ctx.i18n.register('myPlugin', {
  en: { 'panel.title': 'My panel' },
  zh: { 'panel.title': '我的面板' },
})
```

An incomplete third-party catalogue degrades per key (missing keys fall back
to `en`, then to the key) without affecting the rest of the UI.

## Gates (all in CI)

| Gate | Command | What it checks |
|---|---|---|
| Locale parity | `pnpm check:locales` | Every shipped catalogue has identical en/zh key sets |
| No hardcoded strings | `pnpm check:i18n-gate` | Zero hardcoded UI text in tsx |
| Full gate | `pnpm check` | typecheck + lint + test |

The codebase maintains zero hardcoded strings and zero allowlist exceptions.
If future exceptions are ever necessary, `i18n-allowlist.txt` at the repo root
can be used with `file :: text` and `# reason`. Keep it minimal.
